Lesson 1 · Guide part 1

Your website lives in three places

Your Mac, GitHub and the web host each keep their own copy of the site. Each copy changes only when you do the step for it.

1. Your MacThe project folder. You edit and build here.
git push →← git pull
2. GitHubBackup plus full history. Visitors never see it.
upload the contents of public/
3. Web hostThe live website. This is what visitors see.
PlaceWhat it is forHow it changes
Your MacWhere you edit files and build the pagesYou edit, then run python3 build.py
GitHubA safe copy of the project and every past versiongit push (Mac → GitHub), git pull (GitHub → Mac)
Web hostThe live site at sensecellar.comOnly when you upload public/
Key idea

These are three separate places, and each update is a separate step. Pushing to GitHub does not change the live website. Editing a file on your Mac does not change GitHub until you commit and push.

Lesson 2 · Guide part 2

Source files vs built files

This is the most important idea in the guide. You edit a small set of source files. The build turns them into finished pages.

The one-sentence answer

The footer is written once in partials/_footer.html. The build copies it into every page, because a web host can only send complete pages. So you edit the one source file and rebuild, and never edit the copies.

It works like mail merge

In Word, one letter template with «Name» fields plus a list of names produces 100 printed letters. Your website works the same way.

Mail mergeThis website
Letter template with «Name» fieldstemplates/*.html and partials/*.html, with {{key}} fields
The list of names and addressescontent/zh-hk.json, content/en.json, data/*.json, article .md files
The "Merge" buttonpython3 build.py
The printed lettersEverything in public/zh-hk/ and public/en/

To change the letterhead, you fix the template and merge again. You don't correct 100 printed letters by hand. If you did, the next merge would print over your corrections.

What the {{ }} signs mean

  

    

      
You writeThe build replaces it with

      
        
{{footer.hours}}The text at "footer" → "hours" in content/zh-hk.json (or en.json for English pages)

        
{{site.social.instagram}}The value at "social" → "instagram" in data/site.json

        
{{>_footer}}The whole file partials/_footer.html

        
{{@price_table}}Something the build generates itself (here, the price table from data/plans.json)

      
    

  

  
The build checks every page. If a {{ }} has no value (usually a typo), it stops and tells you which file to fix.


  
How to spot a built file

  
Every built page starts with a comment like this:

  
<!doctype html>
<!-- Built by build.py from templates/club.html and content/en.json. Do not edit this file: the next build replaces it. -->

  
If you open a file and see this line, close it and edit the files it names instead.


  
Why not let the browser put the pieces together?

  
It's possible, but worse: the page appears in stages, and search engines may miss content. Building complete pages in advance is the standard approach. Tools like Jekyll, Hugo and Eleventy work the same way, and build.py is a small version of them.

      The words, explained
      
  
      
    
      Repository (repo)
      The project folder plus its complete history.
      Like a binder with every draft kept.
      
    
      Commit
      A saved snapshot with a short message. It stays only on your Mac until you push.
      Like a save point in a video game.
      
    
      Push
      Send your new commits from your Mac to GitHub.
      Uploading your save points to the cloud.
      
    
      Pull
      Fetch new commits from GitHub to your Mac.
      Downloading save points made elsewhere.
      
    
      Branch
      A separate line of work, so you can make changes without touching the official version.
      A photocopy of the document to scribble on.
      
    
      main
      The main branch: the official version of the project.
      The master copy.
      
    
      Checkout / switch
      Change which branch your folder shows. The files on your Mac change to match that branch.
      Swapping which binder is open on your desk.
      
    
      Merge
      Bring one branch's commits into another, e.g. finished work into main.
      Copying approved edits into the master copy.
      
    
      Pull request (PR)
      A page on GitHub that proposes merging a branch into main. You review it, then click Merge.
      Asking for sign-off before updating the master copy.
      
    
      Fast-forward
      A merge where main just moves forward, because nothing new happened on main meanwhile.
      Adding pages to the end of the binder: nothing to reconcile.
      
    
      Ahead / behind
      "ahead 2": your Mac has 2 commits GitHub doesn't. "behind 4": GitHub has 4 your Mac doesn't.
      
    
      Untracked file
      A file Git doesn't know about, e.g. the app 2.html copies iCloud made.
      A loose sheet that isn't in the binder.
      
    
      .gitignore
      A list of files Git deliberately ignores, e.g. .DS_Store, _preview/.
      A "do not file" list.
      
  
      

  
      Why we didn't switch to main before the merge
    
      Switching to a branch makes your folder show that branch's files. Old main didn't have the 20 guides yet, so your folder would have looked as if the work had vanished. Nothing would have been lost (it was safe on the other branch), but it would have been confusing. After the merge, main had everything, so switching was safe. Step 5 of the playground shows exactly this.

      Safe vs risky
      
  
      
    
      Safe: can be undone
      
      
      • Commit, push to a branch, pull
      • Opening a pull request
      • Switching branch after committing
      
    
      Be careful: ask first
      
      
      • Anything with --force, reset --hard or clean
      • Deleting a branch that has not been merged
      • Deleting untracked files: Git can't restore files it never saved
      • Switching branch with uncommitted changes
      
  
      
  
      Golden rule
      When unsure, run git status and ask before doing anything that says force, reset or delete.

      Possible later: automatic publishing
      
  
      
    
      Today
      You upload by hand
      Push backs up to GitHub. A separate upload of public/ publishes. Mistakes on GitHub never reach visitors by accident.
      
    
      Possible later
      The host publishes from GitHub
      Hosts such as Netlify or Cloudflare Pages can publish automatically whenever main changes. That saves the upload step, but main then is the live site, so you'd use branches and pull requests for every change.
      
  
      
  
      Something to decide once you're comfortable with Git.

      Getting clear answers
      
  
      Tips from our sessions for asking Claude, or any helper, so the answer fits what you want.
      

  
        
    
      • Answer options with the number or name. When offered "1, 2 or 3", reply "2" or "open a pull request". A "yes" can't be matched to one option.
        • 
    
      • Say exactly which part is unclear. "I don't understand fast-forward" gets a better answer than asking the whole question again.
        • 
    
      • Ask for the level you want: "explain briefly", "explain as if I'm new to this", "give me a step-by-step".
        • 
    
      • Before anything risky, ask: "What will this change, and can it be undone?"
        • 
    
      • When you stop an action, add one line saying why, e.g. "don't change main yet". Then the next suggestion can fit.
        • 
    
      • State the goal and the limits together, e.g. "Push everything to GitHub; the live site is separate."
        • 
    
      • Ask "where do I edit this?" rather than editing a file in public/.
        • 
    
      • End with: "Summarise what changed and what I need to do next."

      The "app 2.html" copies
      
  
      Your project is inside Documents, which iCloud syncs. When many files change at once (a git pull, switching branch, a full rebuild), iCloud sometimes saves a second copy named … 2.html instead of replacing the file. On 22 Oct we found and deleted 48 such copies. All were exact duplicates.
      
  
      
    
      The fix
      Move the project out of iCloud, e.g. to a Projects folder in your home folder. GitHub is already your backup. After moving, reopen the folder in VS Code.
      
    
      Until then
      After a pull or rebuild, run git status and look for files ending in  2. If one is identical to the original, delete it. If it's different, ask first.
